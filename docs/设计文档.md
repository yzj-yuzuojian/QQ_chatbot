# 设计文档

记录**为什么这样设计**，以及被否决的方案。想改代码之前请先读这里。

---

## 1. 商业模型决定了架构

### 约束

| 约束 | 来源 | 对架构的影响 |
|---|---|---|
| 运营方不承担 LLM 费用 | 成本不可控 | 客户必须自备 key，且**没有**兜底路径 |
| 单机、小内存服务器 | 3.6GB / 4 核 | 不能用向量数据库、不能用 torch |
| 面向中文个人用户 | QQ 场景 | 必须处理中文分词、必须有隐私合规 |
| 20–100 客户规模 | QQ 个人主体限制 | 暴力检索够用，不需要分布式 |

### 客户自备 key 的后果

这不是"加个配置项"那么简单，它会渗透到每一层：

- **未配置时必须硬拒绝**，不能"先用平台 key 顶着"
- 后台任务（摘要、事实抽取）也要走客户 key，否则会偷用平台额度
- 客户 key 会失效、会欠费、会没有某个模型 —— 每种情况都要有话说
- key 必须以密文存储，否则一次数据库泄露就是全部客户资产泄露

### 三层拦截

```python
# ① 命令层
if not cfg.get("key_cipher"):
    return NOT_CONFIGURED, True

# ② 请求前
async def resolve(self, user_id: int) -> Provider:
    if not cipher:
        raise NoProvider("no_key")

# ③ 启动断言 —— 最关键的一层
def assert_no_default_provider() -> None:
    for var in ("PLATFORM_LLM_KEY", "OPENAI_API_KEY", "ANTHROPIC_API_KEY"):
        if os.environ.get(var):
            raise SystemExit(f"检测到 {var}，本项目禁止平台兜底 key")
```

**为什么第 ③ 层不能省：**

异步任务（摘要、向量索引、事实抽取）走的是任务队列，**不经过消息链路**。前两层拦不住它们。如果环境里恰好有个 `OPENAI_API_KEY`（很多部署环境默认带），后台任务就会悄悄用平台的钱。

启动即失败比运行时静默烧钱好。

## 2. 记忆：为什么是三层

### 问题

客户三个月后回来，说「我那只猫咋样了」。

- 只存最近 N 条 → 三个月前的对话早被挤掉了
- 全量塞进 prompt → token 爆炸，成本不可接受
- 只用向量检索 → 检索不到"叫什么名字"这类高频事实，且**远期内容召回不稳**

### 方案

```
┌─────────────────────────────────────────────┐
│ 事实卡（facts）                              │
│   "养了猫：团子" "对芒果过敏"                  │
│   永久保存，每轮注入 prompt                    │
│   成本：约 50 token                          │
├─────────────────────────────────────────────┤
│ 滚动摘要（summary）                          │
│   每 20 轮压缩一次，保留要点                    │
│   覆盖"中期"（几周前）                         │
│   成本：约 150 token                         │
├─────────────────────────────────────────────┤
│ 向量检索（vectors）                          │
│   最近 2500 条，语义匹配                       │
│   覆盖"近期细节"                              │
│   成本：约 200 token                         │
└─────────────────────────────────────────────┘
```

**分层而非全量**，是因为三层的更新频率和稳定性完全不同：

- 事实几周才变一次 → 可以每轮都带
- 摘要每 20 轮变一次 → 可以常带
- 细节每轮都变 → 只能按需检索

### 为什么事实卡跨人设共享

`facts.persona_id = ''`（空串表示共享），而消息是 `persona_id = 'p<id>'`。

客户从「猫」切到「发小」，角色变了，但**"你是谁"不该变**。如果事实也隔离，切一次人设机器人就失忆，体验很差。

代价：删人设时不能连带删事实（否则切回来就忘了你是谁）。代码里 `delete_persona` 显式保留 facts。

## 3. 中文检索：踩过的坑

### 坑一：SQLite FTS5 对中文失效

实测：

| tokenizer | 查「团子」 | 结果 |
|---|---|---|
| `unicode61` | 2 字中文 | **0 条** |
| `trigram` | 2 字中文 | **0 条** |
| 自研 bigram | 2 字中文 | 命中 |

原因：`unicode61` 按空白和标点切词，中文没有分隔符，整句被当成一个 token。`trigram` 需要至少 3 个字符。

解决：写入时把中文切成 bigram（「团子很能吃」→ `团子 子很 很能 能吃`），查询时同样切。

### 坑二：bm25 不能当排序器

bm25 有文档长度惩罚。实测把一句短消息排到了真正相关的长消息前面：

```
查询：面试
候选 A（短）："面试完了"              bm25 更高
候选 B（长）："明天十点去字节面试，很紧张"  ← 真正该排第一
```

短文档因为长度惩罚小反而得分高。

解决：**bm25 只做召回，排序用自研打分**：

```python
score = 0.55 * 覆盖率      # 查询词在片段里出现了多少
      + 0.30 * 长度增益     # 稍长的片段信息量更大
      + 0.15 * 时间衰减     # 越新越优先
```

### 坑三：不是每句话都该检索

如果每条消息都检索：

- 成本翻倍（每次多一次 embedding 调用）
- 延迟翻倍
- 「嗯」「好的」这类消息检索结果全是噪音，反而干扰回复

解决：只在命中触发词时才检索。

```python
TRIGGERS = [
    r"还记得", r"之前", r"上次", r"我以前",
    r"我.{0,6}(什么|啥|哪|几|多少|谁|怎样|怎么样|如何)",   # 第一人称询问
    r"(我的|我家|我养|我有|我会|我能|我住|我在|我做|我学)",  # 第一人称所有
    r"我.{0,3}(多大|干嘛|做什么|什么样|行吗|能吗|好吗)",     # 短问句
]
```

实测：**12 个真实问题命中 10 个，18 句闲聊 0 个误报。** 只有 22% 的消息会触发检索。

## 4. 向量检索：为什么不用向量数据库

### 被否决的方案

| 方案 | 否决理由 |
|---|---|
| Milvus / Qdrant | 单独进程，几百 MB 内存，运维复杂 |
| FAISS | 库本身不大，但索引要全量载入内存 |
| pgvector | 需要装 PostgreSQL，为 20 用户不值 |
| 内存暴力检索 | **采用** |

### 算一笔账

实测 10 万条 × 1024 维：

| 指标 | 数值 |
|---|---|
| int8 量化后单条 | 1 KB |
| 10 万条总量 | 100 MB（磁盘） |
| 单次暴力检索 | **11ms** |
| 一次 LLM 回复 | 2500–3500ms |

检索占回复总耗时的 **0.3%**。为了省这点时间引入一个数据库进程，不划算。

### 但内存必须控制

服务器只有 3.6GB，且已经跑了别的东西。

```python
MAX_LOAD = 2500        # 单用户最多载入 2500 条
SCORE_CHUNK = 4000     # 分批反量化，避免一次性解出 2500×1024 float32
BATCH_SIZE = 32        # embedding 批量
```

**为什么要分批反量化：**

一次性把 2500 条 × 1024 维 int8 全部反量化成 float32，需要 2500 × 1024 × 4 = 10MB 临时内存，20 个用户并发就是 200MB。分 4 批处理后峰值降到 40MB。

实测优化效果：5000 条从 **75.31ms** 降到 **22.78ms**（3.3 倍）。

### 为什么用线程池

`numpy` 点积是纯 C 计算，**会阻塞 asyncio 事件循环**。实测 20 人并发时，串行执行让事件循环卡了 963ms，在此期间所有消息都得不到响应。

```python
_CPU_POOL = ThreadPoolExecutor(max_workers=4)

async def semantic_search(...):
    return await asyncio.get_running_loop().run_in_executor(
        _CPU_POOL, _sync_search, ...
    )
```

墙钟时间从 1246ms 降到 **693ms**。

### 为什么存 user + assistant 两种角色

只存 user 消息看起来更省，实测召回率：

| 索引内容 | 召回率（20 用例） |
|---|---|
| 只存 user | 86% |
| 存 user + assistant | **100%** |

因为有些信息是机器人说的（"你上次说你叫林晚"），只索引 user 会丢掉这部分上下文。

## 5. 检索质量：三种方案实测

20 个真实场景问题的召回率：

| 方案 | 召回率 | 说明 |
|---|---|---|
| 纯关键词（bm25 + 自研打分） | 70% | 「我那只猫咋样了」查不到「团子特别能吃」 |
| 纯向量（bge-m3） | 95% | 语义匹配好，但精确名词会漂 |
| **混合（关键词 + 向量加权）** | **100%** | |

混合策略：

```python
# 关键词命中权重 0.45，向量相似度权重 0.55
final = 0.45 * keyword_score + 0.55 * (semantic_score - 0.85) / 0.15
```

减 0.85 是因为 bge-m3 的相似度基线很高（不相关也有 0.8+），不归一化的话所有结果挤在一起。

## 6. 多人设：为什么消息隔离而事实共享

### 数据模型

```sql
-- 消息按人设分线
messages(user_id, persona_id, role, content)   -- persona_id = 'main' 或 'p<id>'

-- 事实共享
facts(user_id, key, value, persona_id)         -- persona_id = '' 表示共享
```

### 为什么不给每个客户开独立数据库

20 个客户 → 20 个 SQLite 文件，备份、统计、迁移全部变成 N 倍工作量。

用 `user_id` 字段区分，配合索引 `idx_messages_user_persona`，查询性能和分库没有可感知差别。

### 为什么删人设要二次确认

删除会连带删掉：

- 该人设的全部消息
- 该人设的摘要
- 该人设相关任务队列项
- 该人设的向量索引

**不可恢复。** 而 `/persona del 2` 很容易误触（比如想删 3 却打成 2）。

## 7. 生图：为什么让模型判断

### 被否决的方案

**方案 A：关键词匹配**

```python
if any(k in text for k in ["画", "图片", "生成"]):
    draw()
```

问题：

- 「你画得真好」→ 误触发
- 「我昨天拍了张照片」→ 误触发
- 「来一张」→ 漏掉

**方案 B：单独一次 LLM 调用判断意图**

问题：额外一次调用 = 额外成本 + 额外延迟（+1.5 秒）。

### 采用方案：同一次调用附带标记

在 system prompt 里加说明，让模型在需要画图时**另起一行**输出标记：

```
【画图能力】
- 客户让你画图时，先正常回复，然后另起一行写：
  [[DRAW:画面描述]]
```

然后用正则抠出来：

```python
_MARKER_RE = re.compile(r"\[\[DRAW:(.*)\]\]", re.S)
```

**实测 5/5 判断正确：**

| 客户说 | 判断 |
|---|---|
| 你好 | 不画 |
| 我今天很累 | 不画 |
| 画一只橘猫 | 画 |
| 给我画张风景图 | 画 |
| 你能发图片吗 | **不画**（问能力 ≠ 要画） |

零额外调用，零额外延迟。

### 正则为什么要用贪婪匹配

描述里可能含单个方括号：`[[DRAW:cat [with hat]]]`

- 非贪婪 `(.+?)` → 截成 `cat [with hat`，正文还残留一个 `]`
- 贪婪 `(.*)` → 正确得到 `cat [with hat]`

代价是一次回复里写两条标记会合并成一条，但实际不会发生（一次只画一张）。

### 为什么生图 key 必须和聊天 key 分开

实测客户的聊天 key：

```
GET /v1/models                → 只有 gemini-3.8-flash-high
POST /v1/images/generations   → 503「分组 gemini 下模型 gpt-image-2 无可用渠道」
```

聊天走 gemini 分组，生图走 image 分组，**中转站里是两个不同的授权**。强行共用一个 key 只会得到 503。

所以 `/setimage` 是独立命令，存独立的密文。

## 8. QQ 协议：踩过的坑

### 坑一：openid 不跨机器人

同一个用户在不同机器人下 `openid` 不同。如果用 `openid` 做主键，换机器人就丢全部记忆。

解决：内部 `user_id` 自增，`identities(appid, openid)` 映射。

### 坑二：被动回复 vs 主动消息

| 方式 | 配额 | 用途 |
|---|---|---|
| 被动回复（带 `msg_id`） | 客户发 1 条 → 可回 4 条 | 正常聊天 |
| 主动消息（不带） | **每月总量很少** | 定时提醒（未实现） |

**所有聊天回复必须走被动回复。** 否则几天就把整月配额吃光，之后客户发消息也收不到回复。

代码里的约束：

```python
if msg_id:
    payload["msg_id"] = msg_id
    payload["msg_seq"] = self.next_seq(msg_id)
else:
    self.gw.log("[send] ⚠️ 无 msg_id，走主动消息（吃配额）")
    payload["msg_seq"] = 1
```

那条日志是给运维的警报：正常运行时应该**永远看不到它**。

### 坑三：msg_seq 必须递增

同一个 `msg_id` 回复多次时，`msg_seq` 必须严格递增，否则 QQ 按重复消息丢弃。

`Sender._seq` 是**连接级**的字典（不是每条消息新建），所以：

```
文字回复 → seq=1
图片（50 秒后）→ seq=2   ✓
```

上限 2000 条，因为回复窗口只有 60 分钟，再老的记录不会再用到。

### 坑四：图片上传必须 JSON + base64

试过三种格式：

| 格式 | 结果 |
|---|---|
| multipart，字段 `file_data` | 400 `40093007 富媒体文件下载失败` |
| multipart，字段 `file` | 同上 |
| **JSON + base64** | **200** |

multipart 时 QQ 把分段体当成 URL 去下载，所以报"下载失败"。

### 坑五：封面图和正文要分开时段发

生图要 30–60 秒。客户发完「画一只猫」就一直等，体验很差。

解决：先回文字（3.5 秒内），图生成好再补发。

```
t=0s    客户：画一只猫
t=3.5s  机器人：好嘞，画着呢，等我一小会儿      ← seq=1
t=51s   机器人：[图片]                        ← seq=2
```

两条都走被动回复（窗口 60 分钟，足够）。

## 9. 隐私与合规

### 为什么 key 不能走 QQ 聊天

QQ 聊天记录永久留存，等于把密钥抄送给第三方（腾讯 + 任何拿到记录的人）。

解决：`/setkey` 只发一次性码（6 位，10 分钟有效），客户在网页填 key。

```python
code = os.urandom(4).hex().upper()[:6]
```

`urandom` 而不是 `random`：后者是可预测的伪随机，6 位码几秒能爆破完。

### 为什么绑定码要"先校验再作废"

错误的顺序：验证码 → 作废 → 校验 key。如果客户 key 输错，码已经烧了，要回 QQ 重新要码。

正确顺序：验证码 → 校验 key → 通过后才作废。代码里 `consume_bind_code` 带 `used_at IS NULL` 条件防并发。

### 为什么打码

```python
# 客户发的密码/身份证/银行卡号，存储前替换成标记
"我的密码是 abc123"  →  "我的密码是 [密钥]"
```

原文不落库，检索也不会命中。代价是机器人确实"记不住"这类信息 —— 正确处理，它本来也不该记。

### 合规要求

- `/privacy` 完整说明存什么、存哪、谁能看
- `/export` 导出全部数据（JSON）
- `/forget` 永久删除（不可恢复）
- 首次使用展示隐私告知（`CONSENT_TEXT`）

## 10. 被否决的方案汇总

| 方案 | 否决理由 |
|---|---|
| 内置人物性格 | 客户想要的角色千差万别，内置等于限制；改由客户自己写 |
| 订阅制收费 | 涉及支付和退款，且要承担 LLM 成本；改 BYOK |
| 向量数据库 | 20 用户规模用不上，见 §4 |
| torch / sentence-transformers | 装完 2GB+，服务器装不下 |
| 关键词判断生图意图 | 误报率高，见 §7 |
| 敏感词过滤 | 误报率高，且中文需要词库维护 |
| 定时提醒 | 见 [功能与缺失](功能与缺失.md#没有定时提醒) |
| 多机部署 | SQLite 单机够用，分布式复杂度不值 |

## 11. 如果要继续做

按投入产出排序：

1. **定时提醒**（需求真实，但要先解决主动消息配额问题）
2. **群聊支持**（代码已有基础，缺真实测试）
3. **敏感词过滤**（合规需要时才做）
4. **多实例部署**（客户超过 100 才需要）

第 1 项的前置问题：**必须先测出主动消息的真实配额**。官方不公开，只能实测。这个数字决定产品能不能做。
