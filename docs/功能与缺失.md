## 二、已知缺失

### 没有定时提醒

**客户说「明天 6 点叫我起床」，机器人会口头答应，但做不到。**

这是最容易被误解的缺失，必须说清楚。

#### 为什么做不到

QQ 发消息有两种方式：

| 方式 | 生效条件 | 配额 |
|---|---|---|
| 被动回复 | 必须带客户消息的 `msg_id` | 客户发 1 条可回 4 条，用不完 |
| 主动消息 | 不需要 `msg_id` | **每月总量很少** |

被动回复的 `msg_id` 有效期 **60 分钟**。

```
客户 23:00 说「明天 6 点叫我」
        ↓ 7 小时后
    到 06:00 该发消息时，msg_id 早已失效
        ↓
    只能用主动消息
```

#### 主动消息配额是多少

**官方没有公开这个数字。**

实测连发 5 条都成功，但没测到上限。这是做提醒功能的**前置未知数**：

- 如果是每月 100 条 → 20 客户每人 5 次就用完，**不够用**
- 如果是每月 1000 条 → 20 客户每人 50 次，够用
- 如果是每月 10000 条 → 完全可以做

**所以做提醒之前必须先测出这个数字。** 测试代价是消耗当月额度，且在测出上限前可能有一段时间发不出消息。

#### 客户现在会看到什么

```
客户：明天 6 点叫我起床
机器人：好，明早 6 点叫你          ← ← 这是谎话
```

**目前没有修。** 修法是改提示词让它诚实：

```
【能力边界】
- 你没有定时提醒功能，不能说"明天叫你起床"
- 客户要提醒时，明确说做不到，建议自己设闹钟
```

你（项目作者）选择了先不改，改为在文档里说明。这个取舍需要使用者知道。

#### 60 分钟内的提醒**理论上可行**

如果客户说「半小时后提醒我」，落在 60 分钟窗口内，技术上可以用被动回复。

**但没有实现。** 需要：

1. 新建 `reminders` 表存 `(user_id, msg_id, trigger_at, content)`
2. `msg_id` 必须落库（现在是内存字典，重启即失）
3. 定时器轮询到点发送

做完整功能给它，还是不做，取决于主动消息配额的实测结果。

### 不能主动发起对话

**只有客户先说话，机器人才能回。**

后果：

- 不能说「早啊，今天过得怎么样」这种主动问候
- 不能做「三天没聊了，最近还好吗」的召回
- 不能做「你的 key 快过期了」的提醒

原因同上：主动消息配额。

**缓解方案（未实现）：** 客户发任意消息时，机器人顺带说一句。但这不是真正的主动触达。

---

### 群聊支持未验证

代码能处理群消息：

```python
event_type = "group" if "group_openid" in data else "c2c"
```

群相关代码路径：

- 收群消息、按 `member_openid` 区分成员
- 群里禁用 `/setkey`（发链接不合适）
- 群里禁用 `/export`（数据不该给别人看）
- 群内发消息用 `/v2/groups/{gid}/messages`

**但是：**

- 只做过单元测试级的验证
- **没有加入真实 QQ 群跑过**
- 不知道群里是否会收到大量无关消息（噪音问题）
- 不知道是否需要 @ 机器人才响应

**如果要上群聊，必须先做真实测试。**

---

### 群内不共享上下文

群里每个人是**各自独立的对话线**：

```
群成员 A：我叫张三        → A 的对话线记住
群成员 B：我叫李四        → B 的对话线记住
群成员 A：我叫什么？      → 答"张三"（不知道 B 也说过话）
```

机器人**不知道"这是一个群"**，也不知道其他成员存在。

这个设计对陪伴场景是合理的（隐私），但如果要做群聊助手（团建安排、共享日程）就不够。

---

### 没有敏感词过滤

平台侧没有任何内容过滤。

**风险：**

- QQ 可能因内容违规封机器人
- 客户可能用它生成违规内容

**为什么不做：**

- 中文敏感词库需要持续维护，误报率高
- 依赖上游模型自身的对齐能力
- 单人维护的词库反而可能给出虚假的安全感

**如果要做，建议：**

- 用现成的开源词库（如 `sensitive-word`）
- 只做**告警**不做拦截（避免误伤正常对话）
- 违规内容记录到独立日志供人工复核

### 其他缺失

| 缺失 | 影响 | 备注 |
|---|---|---|
| 多机部署 | 只能单机跑 | SQLite + fcntl 锁，20–100 客户够用 |
| 监控指标 | 只能看日志 | 没有 Prometheus / Grafana |
| 流式回复 | 首字延迟高 | QQ 不支持 |
| 语音消息 | 不能收发 | 需要额外 TTS/ASR |
| 图片理解 | 客户发图机器人看不懂 | 需要视觉模型 |
| 定时备份 | 需手动或用 cron | 已提供 `cli backup` |
| 多语言 | 只支持中文 | 分词逻辑是中文专用 |
| 管理后台 | 只有 CLI | 用户管理靠命令行 |

## 三、性能与容量

### 实测数据

环境：4 核 / 3.6GB 内存 / Debian 13

| 指标 | 数值 | 测试条件 |
|---|---|---|
| 常驻内存 | 36 MB | 空载 |
| 20 人并发检索 | +133 MB 峰值 | 各 2500 条向量 |
| 20 人并发聊天 | +75 MB 峰值 | 22% 触发检索 |
| 单次回复 | 2.5–3.5 秒 | 含模型调用 |
| 单次检索 | 265ms 平均 | 20 人并发 |
| 批量反量化 | 22.78ms / 5000 条 | 优化前 75.31ms |
| 存储 | 148 MB | 20 客户 × 5000 条含向量 |

### 容量推算

| 客户数 | 内存估算 | 建议 |
|---|---|---|
| 20 | 约 200 MB | ✅ 当前配置够 |
| 50 | 约 450 MB | ⚠️ 需调高 `MemoryMax` |
| 100 | 约 900 MB | ⚠️ 需 2GB+ 内存 |
| 200+ | — | ❌ 换 PostgreSQL |

**当前 `MemoryMax=768M`，适合 20–50 客户。**

### 瓶颈在哪

不在检索（11ms），在**模型调用**（2.5–3.5 秒）。

这意味着：

- 加机器不能提速（瓶颈在上游）
- 并发能力取决于模型的并发限制，不是本机
- 本机几乎不会成为瓶颈

## 五、上线检查清单

```bash
# ① 服务在跑
sudo systemctl is-active qq-companion

# ② 内存正常（应 < 100MB）
sudo systemctl status qq-companion | grep Memory

# ③ 没有异常堆栈
sudo journalctl -u qq-companion --since "1 day ago" | grep -c Traceback
#    应该是 0

# ④ 没有漏传 msg_id（会吃主动配额）
sudo journalctl -u qq-companion --since "1 day ago" | grep -c "无 msg_id"
#    应该是 0

# ⑤ 数据库大小
du -h /var/lib/qq-companion/data.db

# ⑥ key 巡检
.venv/bin/python -m companion.cli check-keys

# ⑦ 确认无平台兜底 key
.venv/bin/python -m companion.cli assert
```

**第 ④ 项最重要**：如果出现非 0，说明有调用点漏传了 `msg_id`，会消耗主动消息配额。配额吃光后客户将收不到任何回复。

## 六、出问题了怎么办

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 机器人不回复 | 服务挂了 | `systemctl status` |
| 机器人不回复 | key 失效 | `cli check-keys` |
| 机器人不回复 | 主动消息配额耗尽 | 看日志有没有 `无 msg_id` |
| 回复很慢 | 上游慢 | 正常，2.5–3.5 秒 |
| 记不住事 | embedding 挂了 | 看日志 `[vector]` |
| 生图不出图 | 客户没配 key / 分组无权限 | 客户发 `/setimage` |
| 内存持续上涨 | 可能的泄漏 | 重启观察，若复现请报 issue |

### 快速诊断

```bash
# 完整日志
sudo journalctl -u qq-companion -n 200 --no-pager

# 只看错误
sudo journalctl -u qq-companion | grep -E "Traceback|ERROR|⚠️"

# 数据库健康
sqlite3 /var/lib/qq-companion/data.db "PRAGMA integrity_check;"
```
